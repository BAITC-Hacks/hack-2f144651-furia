# Кейс и границы продукта

Источник: предоставленное командой задание «Автоматизация формирования заказов поставщикам», прочитанное на RU/KZ/EN. Это краткое изложение для реализации. Оригинал добавляется локально; см. [источники](SOURCES.md).

## Пользовательский результат

Менеджер закупок выбирает склад/область данных и категорию, запускает расчёт, получает рекомендованные закупки по поставщикам, понимает каждое количество, при необходимости редактирует и утверждает, затем выгружает файл. Основной экран — рабочий список закупок, а не чат.

Ценность, которую нужно проверять: меньше ручной консолидации, меньше искажений от разовых заказов, учёт дефицита и сезонности. Денежную экономию без цен и подтверждённого сравнения не обещать.

## Обязательное из задания

| ID | Требование | Как показать выполнение |
|---|---|---|
| M1 | Базовый заказ использует продажи, остатки, путь, категории и прогноз прироста | Контролируемое изменение каждого входа изменяет соответствующую компоненту/результат в тесте без насыщения |
| M2 | Сезонность и устойчивый рост | Прогноз меняется по сезонам; повторяющийся рост отличается от одного всплеска |
| M3 | Оценка упущенного спроса при stockout | На контролируемом примере восстановленная потребность выше расчёта по сырым продажам |
| M4 | Исключение разовых крупных заказов, включая одного клиента | Внесённый разовый крупный заказ не раздувает регулярный прогноз |
| M5 | Группировка по поставщикам и обоснование каждой строки | Список и экспорт содержат поставщика, SKU, количество, срочность и проверяемое объяснение |

Также необходимы: экспорт; поддержка ключевого сценария проверки/корректировки/утверждения; README с методологией, обработкой выбросов и запуском; учёт конфиденциальности и совместимости с учётной системой.

Нельзя отправлять заказ поставщику без подтверждения; нельзя использовать неанонимизированные клиентские данные в расчётах. В MVP отправку вообще не реализовывать. Локальное подтверждение — состояние заявки, не юридический документ и не сообщение поставщику.

## Необязательное из задания

Приоритизация, минимальная партия, условия поставщика, тренды по категориям, отправка. MOQ и срочность можно сделать после основного расчёта: данные частично предоставлены. Графики достаточно ограничить карточкой выбранного товара. Карта маршрутов, перевозчики и трекинг GPS этому кейсу не нужны.

## Требования отбора из присланного положения

- Основная функциональность создаётся в соревновательной части; общие инструменты и технические шаблоны допустимы заранее (5.4.4.2).
- Основной репозиторий — только выданный организатором; подтверждённый прогресс каждый час (5.4.8–11).
- AI-инструменты разрешены; Codex не обязателен без отдельного требования задачи (5.4.12).
- Фиксация версии в 18:00; изменения позднее не оценивают и на Demo Day (5.4.13–14).
- Проект запускается экспертами по README; если не запускается, исправления не принимаются (5.4.15–16).
- Проверка ключевых функций без личных аккаунтов участников; внешние API требуют доступного способа демонстрации (5.6.6).

Технические веса баллов в кейсе не указаны. Не переносить на технический отбор ориентиры Demo Day: 25/20/15/20/20. Никакого доказательства, что количество агентов или обязательный LLM повышают балл, в переданных материалах нет.

## Предложение инженера, не правило организаторов

Python 3.12, Streamlit, pandas, numpy, openpyxl, pytest; без отдельного backend, базы, регистрации и LLM в расчёте. Демонстрируем прогнозирующую модель и объяснимую закупочную рекомендацию. Если организатор требует конкретный AI-компонент, адаптировать после уточнения, не приклеивать декоративный чат.
