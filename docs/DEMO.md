# Демонстрация на 90 секунд

1. 0–15 с: открыть локальный интерфейс, «Загрузить демо». Сказать: «Это синтетический набор для проверки; реальные файлы ещё не предоставлены».
2. 15–30 с: «Рассчитать предложения». Показать 2 поставщика, 4 позиции и риск по датам; не складывать метры и штуки в один показатель.
3. 30–45 с: выбрать Systeme / 000001_. В объяснении и событиях виден разовый заказ анонимного клиента на 1050, разбитый на три документа. У Systeme / 000004 подтверждённый дефицит даёт восстановление около 58.24 единицы.
4. 45–60 с: открыть «Входные таблицы», inbound. Увеличить ближайшую подтверждённую партию для выбранного SKU, сохранить и пересчитать: потребность снизится. Поздняя партия не уменьшает заказ на текущий горизонт.
5. 60–75 с: в «Проверка и экспорт» изменить количество, в том числе на 0, написать причину и утвердить. Сказать: «Утверждение локальное; файл ещё не отправлен поставщику».
6. 75–90 с: скачать XLSX. Показать recommended_qty, final_qty, approval_status, объяснение и лист Calculation. Изменение входов отменяет прежнее утверждение.

Вопросы жюри:

- **Почему такой метод?** Он воспроизводим, показывает компоненты и работает локально без API. Точность на реальном каталоге ещё надо измерить.
- **Как исключён разовый спрос?** Устойчивый порог, группировка клиента/даты, проверки повторяемости и широких пиков. Есть видимые события и переключатель для проверки решения.
- **Где отсутствуют данные?** Клиенты, stockout, сроки и часть остатков/единиц. Есть отдельный импорт и явная блокировка неполного расчёта.
- **Как доказана польза?** Причинными контрольными тестами. Сокращение закупок, экономия и реальная точность пока не измерены.
- **Что нужно для промышленной версии?** Сверка архивов и единиц, согласование правил/1С, тестирование модели на прошлом, журнал и хранение утверждений, разграничение доступа.
