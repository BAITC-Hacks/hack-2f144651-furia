## Согласованный API риска для Frontend

`from ekt.engine import classify_risk`

Вызов: `classify_risk(row, calculation.config["as_of"])`. Вход row — неизменённая строка Calculation.rows (Series или mapping), либо None при отсутствии результата. Даты — канонические календарные даты без timezone. Возвращается отдельный dict, строки и Calculation не мутируются.

| Поле | Значения и семантика |
|---|---|
| calculation_status | calculated — recommended_qty конечное и ≥0; unavailable — отсутствует/NaN/inf/отрицательное количество |
| risk_level | critical — известная risk_date менее чем через 7 календарных дней, включая 0 и прошедшие даты; risk — известная дата ≥7 дней либо движок явно сообщил «Риск дефицита» без даты; none — завершённый расчёт с «Плановый заказ»/«Запаса достаточно» без risk_date; unknown — расчёт недоступен или метаданные риска непригодны |
| days_to_risk | Целое число дней от as_of до risk_date; None, если дата не установлена. Для недоступного расчёта прежняя/чужая дата игнорируется |
| order_required | True при рекомендованном количестве >0, False при 0, None при недоступном расчёте |

Если непустая risk_date не парсится, risk_level=unknown при calculation_status=calculated: известное количество и неизвестный риск не смешиваются. Отсутствующая urgency без даты также не превращается в «без риска». Непригодный as_of вызывает ValueError; UI должен передавать config.as_of, не текущую дату компьютера.

Подключение к существующим подписям: unavailable → «Нужны данные»; critical → «Критично»; risk или order_required=True → «Пополнение»; none и order_required=False → «Норма». Отдельный unknown при calculated показывать как «Риск не определён», а не «Норма». Для корректных канонических строк граница 6/7 совпадает с текущим urgency_label; malformed-строки получают явное unknown. Очередь полноты/качества данных продолжает использовать data_warnings отдельно. В рамках этой передачи UI не подключался.

## Согласованный API применимости детектора

`from ekt.demand import detector_status`

Вызов: `detector_status(scoped_sales, as_of, enabled=calculation.config["remove_oneoffs"])`.

Передать нормализованные sales **одной** комбинации supplier_id / sku_1c / warehouse_scope, отсечённые helper по date ≤ as_of. Не передавать весь Bundle.sales сразу для нескольких товаров. Возвраты приводятся к отрицательному знаку; учитываются только положительные события клиент/дата, без клиента документ/дата, без обоих исходная строка. Разделённые накладные одного клиента за день не увеличивают число событий.

| Поле | Семантика |
|---|---|
| status | disabled при enabled=False (имеет приоритет); insufficient_history при <12 положительных групп; evaluated при ≥12 и включённом детекторе |
| positive_event_count | Число положительных групп на cutoff, не число аномалий и не число строк документов |
| minimum_events | 12 — действующий порог применимости эвристики |

Helper сообщает **допустимость запуска**, не запускает классификацию и не доказывает отсутствие выбросов. Для completed demand result при evaluated: events — найденные события; applied показывает, было ли исключение реально использовано после сверки с месячным итогом. build_demand использует тот же helper для существующих предупреждений. Monthly-only история даёт 0 событий для детектора накладных; нельзя трактовать её как проверенную.

UI: disabled → «Аномалии не проверялись: детектор выключен»; insufficient_history → «Недостаточно истории: n из 12, требуется проверка»; evaluated + пустые events → «Эвристика выполнена, события не найдены» с оговоркой об ограничениях. Нельзя писать «Аномалий нет». Без customer_id клиентская повторяемость не установлена даже при evaluated; сохранять предупреждение движка. По events.applied=False не уменьшать demand повторно и не прибавлять imputed к forecast.

## Существующий walk-forward JSON: контракт будущего экрана качества

Никакого нового модуля/формата оценки не добавлено; scripts/evaluate_forecast.py и forecast.py не менялись. Формат version=1:

| Путь | Как показывать |
|---|---|
| format_version, data_mode, source_data_modes | Версия и происхождение. synthetic явно показывать как синтетику, не оценку партнёра |
| config.cutoffs, config.horizon_days | Cutoff включён в обучение; целевые даты cutoff+1 … cutoff+H, H от 1 до 730 |
| config.stockouts_known_at_end | Явное допущение знания stockout на дату окончания; false по умолчанию |
| config.growth_plan | omitted_no_knowledge_timestamp: исторические планы роста исключены |
| input_fingerprint, reproducibility | Идентификатор входов/config, версии Python/numpy/pandas и хеши исходников |
| series[] | supplier_id, sku_1c, warehouse_scope, unit; не суммировать MAE разных единиц |
| folds[].cutoff, status | ok или unavailable. У unavailable есть reason, нет scores/predictions/счётчиков — нельзя подставлять нули |
| training_end, seasonal_source, prior_known_as_of | Последняя наблюдаемая дата обучения, источник сезонности и верхняя дата знания выбранной области prior. prior_known_as_of может быть null и не доказывает историческую доступность всех остальных данных |
| train_excluded_qty, train_imputed_qty | Преобразования только обучения, не корректировки holdout-факта |
| n_observed, n_missing | Число известных фактов и неизвестных дней, сумма равна H для ok |
| n_stockout_observed, n_available | Наблюдаемые дни stockout и наблюдаемые дни вне них; сумма равна n_observed |
| n_common | Дни вне stockout, где доступны факт и все три модели. Покрытие показывать как n_common/H вместе с другими счётчиками |
| predictions[] | date ISO, actual / production / raw_mean / seasonal_naive nullable, stockout boolean. Null не превращать в 0 |
| warnings, limitations | Показывать рядом с метриками, а не скрывать за общей оценкой «точности» |

Три модели: production (текущий неизменённый прогноз), raw_mean (среднее raw по покрытым дням обучения до исключений/компенсации), seasonal_naive (наблюдавшиеся продажи той же даты предыдущего года, 29 февраля → 28 февраля; нет доступного лага ≤cutoff → null).

Три представления scores и summary:

- common_available: все модели на одной маске наблюдаемых дней вне подтверждённого stockout;
- production_raw_available: только production/raw_mean на общей парной маске, полезно без годового лага;
- all_observed: включая цензурированные продажи stockout и разовые события, маска конечного прогноза может отличаться между моделями. Не называть точностью скрытого регулярного спроса.

Объект каждой метрики: n, absolute_error=Σ|y−ŷ|, absolute_actual=Σ|y|, mae, wape, undefined_reason. WAPE — **доля**, UI переводит в проценты. При n=0 обе метрики null, причина no_observations. При Σ|y|=0 WAPE=null, причина zero_actual_denominator; MAE при этом может быть известна, даже равна 0.

summary объединяет ошибки/наблюдения внутри одного ряда, а не усредняет MAE/WAPE срезов. Независимая регрессия: четыре ошибки по 10 и две по 5 при actual=20 → n=6, Σошибок=50, Σ|y|=120, MAE=50/6, WAPE=50/120. Ещё два дня без факта остаются null. Нет годового лага → common_available.n=0, но парная метрика известна. Пересекающиеся горизонты считают отдельные пары cutoff/target, не уникальные календарные дни.

Проверки cutoff/утечки сохранены: пересборка demand на каждом срезе, date/coverage_end≤cutoff, фильтрация known_as_of до category fallback, будущие визиты не устанавливают регулярность раньше времени; будущие продажи/месяцы/prior/growth/остатки не меняют прогноз. Скрипт оценки не подбирает модель по метрикам.

Ограничения: нет timestamps получения/поздних исправлений продаж, monthly, stockout, growth. Продажи и месяцы предполагаются известными на date/coverage_end; историческая проверка доступности без snapshots невозможна. По умолчанию stockout используется только для ретроспективной маски scoring. Флаг end-date — анализ чувствительности, не подтверждённый факт. Восстановленный спрос и равномерно распределённый месячный итог не являются наблюдаемой целью. Дневная оценка исключает несходящиеся/недетализированные месячные периоды; внутренние пробелы между накладными предполагаются нулевыми только при полноте выгрузки. Неизвестный stockout может сохранять цензурирование.

## Предложения ABC/XYZ и излишка — не реализованы и не согласованы

Это проекты методик для решения интегратора/владельца данных. Категории и признаки товара не назначались.

- ABC по стоимости потребления: предложенное окно — последние 12 полных месяцев; нужны согласованные чистые количества в базовых единицах, закупочная цена за единицу с датой действия, валюта/НДС и правила курсов, ключ supplier+SKU, полнота периода. Предложенные доли накопленной положительной стоимости: A до 80%, B до 95%, C остаток. До внедрения согласовать включение пересекающего порог товара (предложение: по доле до его включения), обработку равных стоимостей, возвратов/отрицательных итогов, новых и неактивных товаров. Нулевая/неизвестная стоимость → категория неизвестна, а не C по умолчанию. Без цен не подменять стоимостной ABC количеством разных единиц.
- XYZ по вариабельности регулярного спроса: предложенное окно 24 полных месяца, минимум 12 пригодных месяцев для предварительной оценки. Сначала убрать влияние календарной длины месяца и подтверждённой сезонности; CV=population_std/mean месячного дневного уровня. Предложенные границы X≤0.10, 0.10<Y≤0.25, Z>0.25. Нужны полнота продаж, версии очистки и сезонности, подтверждённые stockout/оценка доли imputed; допустимую долю восстановления и влияние тренда согласовать отдельно. Mean≤0, короткая/неполная история → unknown; прерывистый спрос с нулевыми месяцами требует отдельной оценки интервалов, не автоматического Z. Эти пороги не считаются проверенными на данных EKT.
- «Излишек»: возможный кандидат в единицах = max(A+I−D−S,0) за явно выбранный горизонт H; это предложение индикатора, не изменение заказа. До включения согласовать, считается ли путь будущим излишком или только текущий available, горизонт покрытия/сервисный уровень, возвраты поставщику, срок годности, резерв и MOQ. Нужны актуальный scope, ETA/статус, спрос, safety, закупочная цена/валюта для денежной оценки. Неизвестный вход → unknown. Высокий запас не доказывает неликвидность; просроченный/неподтверждённый путь не подставлять.

## Сделано

**E1.** В исходном детекторе три сходных по объёму заказа разных клиентов за ≥14 дней считались регулярными: исключалось 0 вместо 3000. Повторяемость теперь устанавливается только для того же customer_id. Положительные документы клиента за день по-прежнему складываются. Постоянный крупный клиент и массовый пик разных клиентов сохранены. Если customer_id отсутствует, похожие документы не доказывают клиентскую регулярность.

**E2.** Для <12 положительных событий добавлено явное предупреждение о неприменимости детектора и необходимости ручной проверки. Оно проходит через DemandResult в data_warnings. Пустые events больше не выглядят свидетельством отсутствия аномалий. При отключении детектора тоже есть предупреждение. Автоматически менять числа короткой истории не стали.

**LOG-01.** Новый файл заранее предложен как `scripts/evaluate_forecast.py`, уже разрешённый ENGINE в AGENT_PLAN. Вместо предлагаемого в TASKS нового production-модуля используется автономная диагностика с существующими Bundle/build_demand/forecast. Никакого нового production-контракта. Expanding windows, отдельное обучение в каждом cutoff, текущий прогноз и raw mean / seasonal-naive, MAE/WAPE, общая маска сравнения, null при нулевом знаменателе/нет наблюдений, отдельные stockout-метки, локальный канонический ввод и детерминированный JSON с fingerprint/версиями/хешами исходников.

Обнаружены и исправлены два нарушения безопасного использования cutoff, без подбора модели по метрикам:

1. В production будущий prior категории мог вытеснить уже известный prior поставщика. Фильтрация known_as_of теперь предшествует выбору области. Числовая регрессия: январь 10/день, известный множитель февраля 2 → 420 на 21 день; раньше добавление ещё неизвестного prior категории меняло результат на 210.
2. forecast() принимал DemandResult, построенный после cutoff, и использовал будущее. Теперь такой вызов получает ValueError с требованием заново вызвать build_demand. Формы публичных функций и dataclass не изменены; стандартный calculate и UI продолжают работать.

Числовые сценарии:

- 20×10 + три разовых клиента ×1000 → raw 3200, excluded 3000. Тот же крупный клиент на 1/11/21 января → excluded 0. Три разных клиента в один день → широкий пик, excluded 0. Три документа одного клиента в один день → одно событие 3000.
- Будущие визиты не устанавливают повторяемость задним числом: cutoff 15 января исключает два события по 1000; на 21 января есть три регулярных визита за 20 дней, исключение 0.
- 10×10+1000 за 11 дней → excluded 0, 100/день, прогноз 2100 на 21 день, заказ 2300 с safety=2, предупреждение `11 < 12`. При 12 событиях из 11×10+1000 уже исключается 1000.
- Прогноз при expanding cutoff: первые 10 дней по 10 → 10/день; после следующих 10 дней по 20 → 15/день. Будущие продажи и незавершённый месячный итог не меняют ранний прогноз.
- y=[0,10,20], прогноз=[2,8,25] → MAE 3, WAPE 0.3. Нулевой знаменатель → null даже при нулевой ошибке; отсутствие факта не заменяется нулём.
- Один stockout-день с фактом 0 между двумя днями по 10: по доступным дням ошибка постоянного прогноза 10 равна 0; по всем продажам MAE=10/3, WAPE=0.5. Восстановленная величина не становится ground truth.
- 20 доступных дней по 10, затем 10 stockout-дней: при явном допущении знания интервала к его концу train_imputed=100; до конца интервала и в консервативном режиме — 0.
- Проверены prior точно на cutoff / после cutoff, отсутствие мутации входов, високосный год, отсутствие годового лага, месяцы без детализации и несходящиеся итоги, полностью stockout-горизонт и отсутствие истории.

## Контракт и ограничения / интегратору

- Реальные архивы не переданы. Ни качество на партнёрских данных, ни точность ненаблюдаемого спроса не подтверждены.
- Нет дат получения/исправления продаж и месячных итогов: предполагается известность на date/coverage_end. Нет known_as_of у stockout/growth: growth из оценки исключён, stockout-компенсация по умолчанию отключена. Флаг знания на end_date — явное предположение, не доказательство и не новый контракт. Нужны исторические snapshots для строгого знания во времени.
- Основной дневной benchmark исключает месячные периоды без сходящейся детализации; отдельная месячная оценка не реализована. Полнота выгрузки между накладными предполагается, неизвестные stockout остаются нераспознаваемыми.
- Порог 12 и правило повторяемости — эвристики; пустые events не гарантируют нормальность. Без customer_id нельзя надёжно отличить постоянного крупного клиента от разовых заказов.
- Production API формой не изменён; неправильное переиспользование будущего DemandResult теперь явно отклоняется. Потребителям forecast следует передавать результат build_demand с соответствующим cutoff.
- **LOG-02: конфликт назначения** — TASKS относит review.py к Logic, AGENT_PLAN закрепляет его за LEAD. review.py не менялся. Требуется решение LEAD о владельце и политике row_id; LOG-02 не закрыт этой передачей.
- Новый production-модуль оценки из формулировки TASKS не создавался: отдельный scripts/evaluate_forecast.py уже был назначен ENGINE/E4. Интегратору следует согласовать это описание в backlog.
- schema.py, UI, shared fixtures, зависимости и STATUS не редактировались. STATUS обновляет LEAD после приёмки.
- Следующий шаг интегратора: принять результаты и обновить STATUS/TASKS. Первоначальный patch проверен через `git apply --check` на чистой базе; применённые файлы совпали с рабочим деревом.
