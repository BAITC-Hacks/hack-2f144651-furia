## BE-01: отсутствующая и пустая таблицы

Раньше `merge_tables` пропускал любую пустую таблицу. Теперь канонический импорт
отмечает реально найденные таблицы приватным `DataFrame.attrs["_ekt_canonical_table"]`
с именем таблицы. `merge_tables` заменяет непустые таблицы как раньше, а пустые —
только с соответствующей отметкой. Созданные `Bundle` отсутствующие таблицы такой
отметки не имеют. Отдельных полей Bundle и дополнительных колонок не добавлено;
публичные сигнатуры сохранены.

CSV/ZIP/XLSX с заголовками `inbound` без строк очищает inbound и сохраняет sales,
если sales не присутствует в файле. Повторные файлы применяются последовательно:
последняя присутствующая версия таблицы побеждает, включая пустую. Ошибка в любом
файле не изменяет предыдущий Bundle.

Для явной очистки нужны хотя бы заголовки `REQUIRED[name]` из существующей схемы.
Полный набор SCHEMAS подходит. Пустой файл, пустой лист и недостаточные заголовки
вызывают ValueError. Непустые неполные таблицы по-прежнему разрешены для дальнейшего
редактирования; полная валидация выполняется при расчёте.

Отметка проверена через `Bundle.copy()` и `normalize()` на зафиксированной версии
pandas. Это внутренняя метаинформация импорта в памяти. Пересоздание DataFrame без
attrs не сохраняет команду очистки. Обычный вручную созданный пустой Bundle, как
и прежде, ничего не очищает при merge; для очистки используйте канонический импорт
с заголовками либо `edit_table` с пустой таблицей.

## BE-02: стратегия идентификации

Ключ сопоставления — точный кортеж **всех нормализованных значений записи без
PROVENANCE**, включая дополнительные бизнес-столбцы. Набор колонок берётся из
обеих таблиц, порядок колонок фиксируется; пропуски сравниваются единообразно.
Позиция и pandas index не участвуют. Бизнес-KEY/документ сами по себе недостаточны:
несколько продаж одного SKU в одном документе могут быть разными записями.

Все четыре поля provenance сохраняются только при единственном совпадении в
исходной и сохранённой таблице. Новые/изменённые записи и неоднозначные дубли
получают `source_file=manual`, `data_mode=manual`, `source_sheet=<таблица>`;
source_row заполняется обычным normalize для ручного набора. При дублировании
manual получают все неразличимые копии. Если из прежних одинаковых строк с разными
источниками остаётся одна, она также manual. Количества и строки не суммируются
и не удаляются автоматически. Присланные редактором поля provenance игнорируются.

Новые ID или бизнес-поля не введены, Bundle и интерфейс UI не менялись. Сравнение
выполняется по точному содержимому без отдельного ID. Эквивалентные представления
чисел, дат, boolean и пропусков сравниваются после существующего normalize.

Сохранена возможность backend-клиента исправить или очистить невалидную raw
таблицу: сначала нормализуется исправленный набор. Если исходную таблицу нельзя
нормализовать, все сохранённые строки остаются manual. Неверный новый ввод
по-прежнему вызывает ошибку без мутации входов. Этот случай найден независимым
ревью, исправлен и покрыт четырьмя дополнительными регрессиями.

**Предел без постоянного ID:** удаление B и изменение A до полного содержимого B
неотличимо от сохранения B. Метод подтверждает совпадение данных, а не физическую
историю записи. Если нужен журнал таких действий, потребуется отдельное
согласование стабильных ID/журнала с интегратором. В этом этапе они не добавлялись.

### Исправление и обнаруженные ограничения

**Исправлено в BE-03:** месячные остатки Systeme имеют заголовки A «№», B «Номенклатура»,
C «Номенклатура.Код». Адаптер брал название из A и мог перезаписывать имя товара
порядковым номером. Теперь колонка имени определяется по заголовку перед кодом;
сохраняется совместимость с IEK (имя в A) и прежним макетом A «Наименование». Добавлены отдельные
синтетические регрессии обоих поставщиков и проверки исходных названий в opt-in
тестах. Формулы расчёта, схема Bundle и UI не менялись.
Независимое ревью проверило выбор правильной колонки имени на всех строках
stock-отчётов: несовпадений не найдено.

**Исходные данные требуют исправления:** в динамике IEK — 18 пустых количеств,
Systeme — 13. В полном импорте до `a9decc7` неизвестные сохранены, `validate`

Полный набор пока нельзя выдать за готовый к расчёту.
Строки не удалялись, количества нулями не заменялись.

**Новый строгий отказ IEK:** после интеграции DATA `a9decc7` импорт выявил

### Правило импорта

Адаптер собирает все известные кандидаты количества по SKU и полю. Systeme
получает `order_multiple` из MOQ E и monthly D; IEK сохраняет выбранную пользователем
семантику `unknown` / `minimum` / `multiple`. Различающиеся значения останавливают
импорт с ValueError: поставщик, SKU, поле, оба значения, файлы, листы и строки.
Значения выводятся без округления коротким форматом, чтобы близкие числа оставались
различимы. Никакой источник не объявляется авторитетным без подтверждения.

Совпадающие кандидаты выбирают источник детерминированно: MOQ перед monthly,
затем файл/лист/строка. Приоритет влияет только на ссылку для одинакового числа.
Значение и существующее `quantity_rule_source` (`filename:row`) назначаются вместе.
Пустой кандидат не создаёт и не меняет правило или источник. Публичные поля и
формат ссылки не расширены; новые ID не введены.
