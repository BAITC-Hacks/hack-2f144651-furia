# Разделение доработки EKT

Продолжаем существующее приложение. Задания подготовлены к выдаче; наличие промпта
не означает, что исполнитель назначен или работа завершена. Роли назначает LEAD.

Пути от корня repo. Новые файлы разрешены только в своей области; расширение
согласуйте до редактирования. Запускать чужие тесты можно, менять — нельзя.

## DATA — импорт

1. **D1: явные конфликты источников.** В `tests/test_partner.py` Systeme-макет
   содержит monthly=100 и V2=999; сейчас выбирается 100 без сообщения о расхождении.
   Сохранить приоритет авторитетного месячного отчёта, но сообщать SKU/месяц,
   оба значения, источники и правило выбора. Порядок файлов ZIP не должен менять
   результат. Конфликт двух основных отчётов нельзя молча перезаписывать.
2. **D2: форматы ETA.** Сейчас `eta_value(Timestamp('2026-09-24'),
   Timestamp('2026-09-22'))` возвращает None. Проверить datetime/date/Timestamp,
   поддержанные строки и невалидные даты. Для `05.01` при отчёте в декабре не
   угадывать следующий год: явное правило/предупреждение, неизвестная дата остаётся видимой.
3. **D3: канонический импорт и края.** Коды, знаки, пустые/нечисловые значения,
   единицы, scope, дубли, неполные отчёты. Ошибки должны быть понятными; неверное
   значение не должно незаметно становиться отсутствующим. Сохранить API импорта.
4. **D4: оригинальные архивы.** Если предоставлены — инвентаризация 12 XLSX,
   сверка нескольких SKU/месяцев с накладными, знаки, единицы, происхождение
   актуального остатка, полное чтение и время загрузки. Без оригиналов завершить
   доступные проверки на макетах, явно написать «оригиналы не проверены».

Первая передача: D1/D2 с регрессиями и один валидный срез Systeme. Финальная:
оба адаптера, результаты D1–D4 и отчёт покрытия. Сырые записи не публиковать.

## ENGINE — расчёт

1. **E1: повторяемость крупных заказов.** Сейчас повторяемость проверяется по
   близости объёмов всех клиентов. Пример: 20 ежедневных заказов по10 плюс три
   заказа по1000 от разных разовых клиентов 1/11/21 января → excluded=0.
   Не считать это регулярным крупным клиентом только из-за сходства количеств.
   Обосновать классификацию; сохранить постоянного крупного клиента и широкий
   сезонный пик (T11). Не вводить правило «всё крупное исключать».
2. **E2: короткая история.** При <12 групп детектор молча отключён: десять заказов
   по10 и один1000 за11 дней дают прогноз100/день, excluded=0. Добавить явное
   предупреждение о неприменимости детектора/ручной проверке. Отсутствие events
   не должно выглядеть доказательством отсутствия аномалий; автоматическое
   исключение на столь короткой истории не обязательно.
3. **E3: границы M1–M4.** Stockout при пересечениях, частичных продажах и отсутствии
   доступных дней; несходящиеся месячные итоги; неполные месяцы/cutoff; единственный
   план роста; reserve/available; поздняя ETA; MOQ/multiple и неизвестные входы.
   Исправлять подтверждённые дефекты, добавляя независимые числовые регрессии.
4. **E4: ограниченная оценка качества после обязательных исправлений.** В
   `scripts/evaluate_forecast.py` воспроизводимое сравнение модели с raw mean и
   seasonal-naive по прошлым периодам (MAE/WAPE, нулевой знаменатель, cutoff и
   known_as_of). Отдельно обозначать продажи и ненаблюдаемый спрос при stockout.
   Не менять production-модель ради отчёта; при нехватке времени явно отложить E4.

Первая передача: E1/E2 с примерами и регрессиями. Финальная: выполненные E1–E3,
статус E4 и ограничения метода. Общий Bundle и формы результатов не менять самостоятельно.

## LEAD — интеграция и пользовательский путь

1. **L1:** стабильная общая база, исправленный тип unconfirmed_moq, зависимости,
   единый контракт и назначение исполнителей. Остальные изменения schema только через LEAD.
2. **L2:** два поставщика и дополнительные таблицы в UI, видимые ограничения,
   корректная маркировка synthetic/partner/manual, сохранение источников и параметров.
3. **L3:** объяснения и экспорт совпадают с расчётом, ручной ноль и причина,
   утверждение и его сброс при изменениях, текстовые SKU и статус файла.
4. **L4:** поочерёдная интеграция, все тесты, согласованный SHA для REVIEWER,
   возвращение дефектов владельцам и проверка исправлений.
5. **L5:** чистая установка по README, пользовательский сценарий, актуальные
   STATUS/README, короткая демонстрация и честные ограничения реальных данных.

## REVIEWER

Проверяет конкретный интегрированный SHA в чистой копии: установка, все тесты,
независимые примеры M1–M5, UI/утверждение/экспорт и доступность данных эксперту.
Для дефекта — вход, шаги, ожидание, факт и файл/строка. Код не меняет; LEAD
передаёт исправление владельцу.

## Контракты, Git и передача

- Все начинают с одного полного SHA, предоставленного LEAD. Реальные API — в
  [INTERFACES.md](INTERFACES.md); имена из старого комплекта не копировать механически.
- Запрос изменения схемы: пример входа, текущий результат, нужные поля/типы,
  затронутые вызовы и минимальная проверка. LEAD меняет контракт один раз и
  передаёт патч/новый SHA обоим. Несовместимые локальные обходы запрещены.
- Предпочтительна отдельная ветка/копия на исполнителя. В общем working tree
  DATA/ENGINE не делают add/commit/checkout/reset/merge и не устанавливают
  зависимости одновременно. Коммиты выполняет LEAD после проверки diff.
- В своей ветке исполнитель коммитит только свои файлы. Передаёт SHA и способ
  получения объектов: локальная ветка, разрешённая удалённая ветка или patch.
  Push требует отдельного указания; force push не использовать.
- LEAD проверяет область diff, интегрирует одну часть, запускает её тесты и
  общую приёмку. После второй части снова проверяет интеграцию. Чужие изменения
  при конфликтах не стираются; спорное решение согласуется с владельцем.
- Первый handoff отдавайте сразу после проверяемого результата. Полный отчёт —
  по [TEMPLATE.md](handoffs/TEMPLATE.md). Общий STATUS обновляет только LEAD.

## Готовность

Все тесты и M1–M5 проверены; основной пользовательский путь работает; README
воспроизводим; есть отчёты назначенных ролей. Макеты не заменяют реальную проверку:
отсутствие оригиналов отмечается отдельным непроверенным пунктом. Отправка кода и
сдача — отдельные действия с явным статусом, не автоматическое следствие локальной готовности.
