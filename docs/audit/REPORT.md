# Отчёт о работоспособности EKT

**Дата:** 23.09.2026. **Тип:** технический аудит, функциональные проверки и ограниченный нагрузочный эксперимент.
**Начальная база:** `b5b3764615e604fcc174191b2ce0f5a9380cdf56`, официальный `main` после fetch.
**Финально проверенный код:** `89044510d563431b8cc6b6c8f9ca15a6bcf9cb43`, после объединения с командным обновлением UI `9d1a42d`.
**Исполнитель:** Codex, интегратор AUD-01; независимая read-only проверка расчётного ядра: Reviewer Nietzsche (`01a0ce09-a5e7-7ca0-b49a-8b0a8835b2fb`).

## 1. Итог

**Система работоспособна как локальный MVP на согласованных корректных входах, но не готова к бесконтрольной промышленной эксплуатации.** Базовый путь от загрузки до утверждения и выгрузки работает. Все существующие тесты прошли. Вместе с тем дополнительные проверки нашли ошибки, которых текущие тесты не покрывают.

Основные риски: потеря некоторых строковых кодов при импорте XLSX; падение рабочего экрана из-за ошибки автоматически создаваемой выгрузки; неразличимые складские строки в UI; коллизии идентификаторов/подписей и недостаточная устойчивость числовых крайних случаев. На 1000 SKU расчёт занимает около 80 секунд, изменение фильтра вызывает серверную обработку около 6,7 секунды.

Проверка **не доказывает**, что система корректно обработала все реальные данные партнёров, выдерживает произвольный объём или поддерживает заданное число одновременных пользователей. Исходные архивы в этой рабочей папке не предоставлены; существующая командная сверка зафиксировала блокирующие ошибки исходников. Перечень ниже содержит все подтверждённые находки этого аудита, но не является гарантией отсутствия остальных дефектов.

Продуктовый код в AUD-01 **не исправлялся**. Добавлены только отчёт, воспроизводимые синтетические диагностические сценарии, их числовые результаты и задания разработчикам.

## 3. Как работает система

1. **Ввод.** Канонические CSV/ZIP/XLSX либо специализированные отчёты IEK/Systeme читаются локально. `application.py` объединяет таблицы или заменяет поставщика. При неудачном импорте UI публикует ошибку, прежний Bundle остаётся доступен.
2. **Нормализация и контроль.** `schema.py` приводит типы, сохраняет строковые ключи и происхождение, проверяет обязательные поля, внешние ключи, дубли, даты и политики. Проверка структуры не подтверждает полноту выгрузки или правильность бизнес-допущений.
3. **Спрос.** `demand.py` отделяет продажи/возвраты, группирует события по клиенту/дате либо документу/дате, обрабатывает разовые события. Месячная история используется как альтернативный источник, не прибавляется второй раз к детализации. Stockout компенсируется только по явно заданным интервалам.
4. **Прогноз.** `forecast.py` использует до 48 полных месяцев, собственную сезонность при достаточном числе циклов, известный на cutoff prior либо нейтральную сезонность. При короткой истории применяется средний уровень с предупреждением. Тренд и дополнительный рост учитываются раздельно.
5. **Заказ.** Для supplier + SKU + warehouse_scope движок проверяет политику и текущий остаток точно на дату расчёта. Из прогноза и страхового запаса вычитает доступный запас и подтверждённый путь в горизонте, применяет MOQ/кратность. Дневной баланс даёт дату риска. Недостаток входов обычно возвращает недоступную позицию с объяснением, а не выдуманный ноль.
6. **Решение.** UI хранит правки по row_id, разрешает ручной ноль, требует причины значимых изменений, сбрасывает утверждение при правках. Фильтр меняет только просмотр. Общий состав выгрузки берётся из выбранных строк, включая скрытые фильтром.
7. **Вывод.** Формируются CSV/XLSX с draft/approved и метаданными. Это локальная выгрузка, не отправка поставщику и не проверенная интеграция с 1С.

Расчёт выполняется в Python-процессе Streamlit, без отдельного HTTP API, очереди задач и постоянной БД. Backend/Logic не импортируют UI. Полный каталог входных таблиц: products, sales, monthly_sales, stock_snapshots, inbound, stockouts, policies, growth_plan, seasonal_prior.

**Не все входные поля превращаются в показатели dashboard.** Например, нет закупочных цен/валют и согласованного ABC/XYZ; стоимость честно обозначена «Нет цен». Неизвестные клиенты, единицы, сроки и дни дефицита не могут быть восстановлены из отсутствующих данных. Сырые продажи на графике и очищенный спрос решают разные задачи.

## 4. Нагрузка

### Условия

- Windows 11 Pro 10.0.26200; AMD Ryzen 7 7435HS, 8 ядер / 16 потоков; ОС видит около 11,69 ГиБ RAM, в начале было свободно около 1,88 ГиБ.
- Python 3.12.14, pandas 3.0.6, Streamlit 1.64.0, существующая `.venv`.
- Два синтетических поставщика, одна область склада, ежедневные продажи, 365 дней; валидные товары, политики, запас и по одной партии пути на SKU. Нет архивов партнёров или клиентских записей.
- Для каждого размера отдельный процесс; ограничение диагностического контроллера: 180 секунд и 800 МиБ RSS. Это **не лимиты приложения**. Все перечисленные сценарии завершились до ограничений.
- Один замер на сценарий, без изоляции от фоновых процессов рабочего компьютера. Значения ориентировочные, не среднее/p95/p99 и не SLA. Часть проверок выполнялась на фоне других лёгких аудиторских операций.
- `UI` означает серверное выполнение Streamlit AppTest, не отрисовку браузерного canvas и не сетевую задержку. В этих замерах AppTest получает готовый Calculation; время расчёта измерено отдельно.

### Практическая интерпретация

- Малые наборы до порядка 100 SKU в проверенном профиле подходят для локального интерактивного пилота.
- 500 SKU обработаны, но расчёт требует заметного ожидания; 1000 SKU обработаны, однако интерфейс уже медленный. Это свидетельство выполненного сценария, **не установленный максимальный размер каталога**.
- Больше 1000 SKU, больше 365 000 продаж в одном прогоне, массовые оригинальные XLSX, 10+ клиентов, длительные серии загрузок и утечки памяти не проверялись. Экстраполировать пределы по одному сжатому ZIP нельзя.
- При умножении складских областей растёт число расчётных позиций. Длинная история, строки/колонки, типы источников и количество файлов влияют независимо от размера ZIP.
- Для production нужны согласованные бюджеты ожидания/памяти, предварительная оценка входов, ограничение совокупного размера, ограниченный кеш, прогресс/отмена, а при подтверждённой необходимости отдельный вычислительный worker. Переход на React сам по себе скорость расчёта не исправляет.

### Уже существующие ограничения

| Участок | Реальное ограничение |
|---|---|
| Streamlit uploader | 80 МБ на файл (`.streamlit/config.toml:5`) |
| Backend reader | 100 МиБ сжатых байт на один вход (`ingest.py:9,25`; `partner.py:95`) |
| Внешний ZIP | до 100 файлов и 100 МиБ суммарных распакованных элементов |

| Горизонт политики | до 730 дней; это не ограничение длины входной истории |
| История расчёта спроса | не более 365×15 дней от первой даты до cutoff; более длинная история даёт ошибку позиции (`demand.py:115`) |

Общего ограничения на всю пачку канонических файлов, суммарные распакованные XML всех XLSX партнёра, число строк/ячеек или кешированные версии **нет**. Предел истории проверяется в расчёте после импорта и не является ранним бюджетом чтения файлов. Эти размеры не тождественны памяти pandas/openpyxl. `cached_partner` задан без TTL/max_entries. Контроллер аудита ограничивал только свои тестовые процессы и не добавлял защиту в продукт.

## 5. Подтверждённые дефекты

Приоритеты: **P1** — блокирует сценарий/опасен для целостности и должен быть устранён перед расширением пилота; **P2** — существенная ошибка в допустимом или граничном сценарии; **P3** — некорректное описание/обслуживаемость. Это приоритеты технического аудита, не оценка частоты случаев на неизвестном production-трафике.

### D01 / P1. Ошибка XLSX прекращает отрисовку рабочего экрана

**Место:** `src/ekt/export.py:8,33`, `src/ekt_ui/review.py:96,109`, `src/ekt_ui/app.py:50`. **Владельцы:** Backend + Frontend.

Импортируемое имя `Synthetic\x0bitem` проходит validate; расчёт строится. `xlsx_bytes` выбрасывает `IllegalCharacterError`. UI создаёт XLSX заранее внутри закрытого popover, поэтому падает до редактора заказа, даже если экспорт не запрошен. AppTest подтвердил исключение и отсутствие `review_editor_key`.

Нужен согласованный контракт для XML-недопустимого текста: явная локализованная ошибка с местом либо документированное преобразование только копии для вывода. Frontend должен изолировать сбой конкретной выгрузки; таблица/правки/CSV не должны исчезать. Не молча менять исходный SKU.

### D02 / P2. XLSX превращает буквальные коды NA / NULL / N/A в пропуски

**Место:** `src/ekt/ingest.py:50`. **Владелец:** Backend.

`pd.read_excel(..., dtype="string")` оставляет стандартное распознавание NA. Воспроизведение: XLSX даёт три `<MISSING>`, аналогичный CSV сохраняет `NA`, `NULL`, `N/A`; код `000001` сохраняется в обоих. Это относится не только к SKU, но и к другим текстовым значениям. Нужна единая семантика пустых ячеек/буквального текста для CSV и XLSX и регрессия на обоих форматах.

### D03 / P2. Разные ключи сталкиваются в одном row_id

**Место:** `src/ekt/engine.py:126`. **Владелец:** Logic, совместимость с Frontend согласует интегратор.

Склейка ключа через `|` не экранирует разделитель: `(S, X|Y, Z)` и `(S, X, Y|Z)` дают одинаковый ID. Получены две строки и лишь одна запись `details`; review отклоняет дубли. UI merge тоже не сможет обработать их. Нужна однозначная сериализация составного ключа, тесты уникальности и отсутствия перезаписи деталей.

### D04 / P2. Fingerprint теряет точность и не всегда отменяет утверждение

**Место:** `src/ekt/schema.py:176`, `src/ekt/review.py:53`. **Владельцы:** интегратор общего контракта + Logic.

`to_json` с точностью по умолчанию округляет небольшие различия. Продажи `10 → 10.00000000004` оставляют тот же fingerprint, но рекомендация меняется `230 → 231`; с пустым override старое Approval возвращает `approved` для нового результата. Это воспроизведение Python API на искусственно малой дельте, а не утверждение, что обычное сохранение формы UI всегда сохраняет approval: UI дополнительно сбрасывает состояние при сохранении входов.

Нужно lossless/согласованное каноническое кодирование чисел в fingerprint и подписи правок. Одной сменой отображаемого округления дефект не исправляется. При изменении версии подписи старые утверждения не должны оставаться валидными.

### D05 / P2. Относительный допуск скрывает существенную ручную правку

**Место:** `src/ekt/review.py:48`; тот же подход в `src/ekt_ui/presentation.py:27`. **Владельцы:** Logic + Frontend-потребитель.

Для рекомендации `1 000 000` значение `1 000 009` признаётся `manager_override=False` из-за стандартного `np.isclose`; утверждение проходит с пустой причиной. Правило допуска должно соответствовать точности количества/единице, а не расти неявно вместе с объёмом. Нужен единый согласованный предикат изменения для UI и Logic, регрессии на больших и дробных количествах, ручной ноль.

### D06 / P2. Числовое переполнение может выдать ложный нулевой заказ

**Место:** `src/ekt/forecast.py:42,74,82`, `src/ekt/engine.py:193–196`. **Владелец:** Logic.

12 положительных конечных коэффициентов prior `1e308` проходят validate. Среднее переполняется, дальнейший прогноз содержит некорректные промежуточные значения; результат агрегируется в прогноз/заказ 0 вместо ожидаемого положительного спроса. Для контрольного нейтрального набора ожидалось 210 прогноза и 230 заказа. Это экстремальный синтетический вход, но недоступный расчёт не должен выглядеть как достаточный запас. Нужны стабильная нормализация и проверки конечности промежуточных/выходных значений.

### D07 / P2. Маленькая положительная кратность роняет весь расчёт

**Место:** `src/ekt/engine.py:60`, обработка ошибок позиции `engine.py:218`. **Владелец:** Logic; диапазоны входов согласовать с интегратором.

`order_multiple=1e-308` проходит validate, затем возникает `OverflowError` в `ceil`, который не относится к перехватываемым ValueError. Нужен контролируемый отказ по входу/позиции с объяснением, без молчаливого нуля и без маскировки любых программных исключений широким catch-all.

### D08 / P2. Проверка внешних ключей раздувает ошибочные данные до проверки дублей

**Место:** `src/ekt/schema.py:114`. **Владелец:** интегратор; Backend передаёт регрессию и предложение.

Три одинаковых товара × три строки продаж создают девять промежуточных строк merge; ошибка дублей возвращается позднее. Рост N×M потенциально исчерпывает память на импортированном ошибочном каталоге. Большой разрушительный пример не запускался: кратность подтверждена безопасным малым примером и кодом. Проверять уникальность раньше или делать membership-проверку по уникальным ключам без many-to-many расширения.

### D09 / P2. Две складские позиции невозможно различить в таблице и выборе аналитики

**Место:** `src/ekt_ui/review.py:61`, `src/ekt_ui/details.py:86`. **Владелец:** Frontend.

Для одного SKU в W и W2 расчёт возвращает отдельные правильные строки. В видимой таблице нет `warehouse_scope`, а обе подписи выбора аналитики одинаковы: `000001_ · Synthetic product`. Техническая связь по row_id сохранена, но человек может выбрать/исправить не тот склад. Нужно показывать область в обоих видах и supplier/SKU/scope в выборе аналитики; не менять глобальный состав экспорта.

### D10 / P2. Тяжёлые операции повторяются при каждом фильтре

**Место:** `src/ekt_ui/app.py:50`, `review.py:96`, `inputs.py:56`, `results.py:20`, `imports.py:102`. **Владелец:** Frontend; оптимизация ядра отдельно у Logic.

CSV/XLSX, ZIP всех входов, нормализация/fingerprint выполняются на rerun независимо от намерения скачать. Закрытые вкладки/expander/popover не откладывают исполнение содержащегося Python. На 1000 SKU обычный фильтр занимает 6,72 с. Нужны lazy-подготовка или ограниченный кеш по версии входов/правок/утверждения/формату. Кеш не должен возвращать старый approved-файл или зависеть от фильтра просмотра.

### D11 / P2. Ограничения отдельных файлов не ограничивают совокупную работу

**Место:** `src/ekt/application.py:13`, `partner.py:168–172`, `src/ekt_ui/imports.py:15`. **Владельцы:** Backend + Frontend, бюджеты согласует интегратор.

Подтверждено чтением кода: последовательная пачка файлов не имеет общего бюджета, каждый вложенный XLSX получает свой лимит, `sorted(xlsx_members(...))` материализует список payload; кеш не ограничен по числу версий. Превышение RAM на максимальных архивах не вызывалось намеренно. Это ресурсный риск, не доказанный внешний взлом: текущий сервер слушает localhost. Нужны совокупные лимиты и ранняя проверка, ограниченный кеш; не увеличивать upload limit как «оптимизацию».

### D12 / P3. Статусы реального импорта устарели в UI и общей документации

**Место:** `src/ekt_ui/imports.py:53`, нижний блок BE-03 в `docs/TASKS.md`, `docs/DEVELOPMENT.md`.

UI пишет «проверены только на макетах», хотя [последний Backend-handoff](../handoffs/backend.md) описывает сверку оригиналов и безопасный отказ. TASKS также содержит прежнее число 18 вместо текущих 20 opt-in проверок и старое описание уже исправленного ложного происхождения MOQ. Сейчас блокируют противоречивые исходные значения, а не тот прежний дефект. Frontend обновляет только текст своего экрана, интегратор синхронизирует общие документы. Не заменять устаревшую фразу недостоверным «реальный импорт полностью проверен».

## 6. Данные и качество анализа

### Реальные архивы

В этой локальной копии `data/` содержит только demo; opt-in переменная с оригиналами для запуска не предоставлена. Архивы с других машин не скачивались, приватные источники не публиковались.

Последняя командная проверка Backend сообщает: код обнаружения конфликтов кратности исправлен, но полный импорт оригиналов по-прежнему блокируется. На той машине получено **2 passed, 18 skipped** с оригиналами: два теста подтверждают правильный отказ, не успешный Bundle. Требуются исправления 15 ячеек MOQ IEK и 31 количества продаж (18 IEK / 13 Systeme), разрешение противоречий кратности Systeme, подтверждение складов, единиц и политик. Это исторические результаты команды из [handoff](../handoffs/backend.md), не повторный замер AUD-01.

### Синтетический walk-forward

Два запуска `scripts/evaluate_forecast.py --demo` с настройками по умолчанию: cutoff с марта по август 2026, горизонт 28 дней. SHA256 обоих JSON: `6747f72b38d1ddc4f0167c568c345cb8c03070a48ee77c27ecc249eb5e94eec1`.

| Синтетический ряд | Общих наблюдений без stockout | WAPE production | WAPE raw_mean |
|---|---:|---:|---:|
| IEK / 000001_ | 162 | 7,54% | 12,76% |
| IEK / 000002 | 162 | 7,62% | 15,01% |
| Systeme / 000001_ | 162 | 64,99% | 67,33% |
| Systeme / 000004 | 152 | 6,93% | 6,81% |

Это сравнение с наблюдаемыми продажами, не с истинным скрытым спросом. Разовый проектный заказ повышает ошибку ряда Systeme / 000001_; его исключение из регулярного спроса и прогнозирование исходных пиков являются разными целями. На последнем ряду среднее чуть лучше production. Нельзя обещать универсальное превосходство, снижение запасов/дефицита или переносить эти проценты на реальные закупки. Разные единицы не суммировались в одну общую точность.

## 7. Известные ограничения, не новые баги

- Нет постоянного хранения набора, правок и согласования. Перезагрузка страницы/потеря процесса требует повторного ввода; экспорт не является полноценным восстановимым состоянием приложения.
- Нет многопользовательской модели, ролей/прав, долговечного журнала действий, конфликтной записи, очереди/отмены заданий. Текущий безопасный режим — локальный, не публичный сервер.
- Нет закупочных цен, валют, согласованной ABC/XYZ-методики, реальной отправки заказа и приёмки формата конкретной 1С. Это не имитируется.
- Дни между накладными без строк трактуются как нулевые при принятом допущении полноты; месячные данные распределяются по дням. Notes/предупреждения обязательны, точность из такого распределения не следует.
- Stockout и клиентская повторяемость требуют реальных подтверждённых интервалов/клиентов; месячный нулевой остаток и номер документа их не заменяют.
- CSS зависит от внутреннего DOM Streamlit; обновление библиотеки требует визуальной регрессии. Массовые браузерные таблицы на 1000+ строк не проверены в реальном браузере этим аудитом, только серверным AppTest.
- Нет проверки восстановления после crash, заполненного диска, длительных загрузок и сетевых обрывов. SAST/SCA/CVE-аудит, резервное копирование и production-deployment не входили в выполненный объём.
