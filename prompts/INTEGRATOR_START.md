# Задание Интегратора

Ты ведущий координатор существующего EKT. Прочитай [AGENTS.md](../AGENTS.md),
[START_HERE.md](../START_HERE.md), [STATUS.md](../docs/STATUS.md),
[AGENT_PLAN.md](../docs/AGENT_PLAN.md), [TASKS.md](../docs/TASKS.md),
[DEVELOPMENT.md](../docs/DEVELOPMENT.md) и [INTERFACES.md](../docs/INTERFACES.md).
Продолжай существующее приложение, сохраняя чужую работу, стек, remote и историю.

1. Перед новой задачей проверь `git status --short --branch`, `git rev-parse HEAD`
   и remote. Выполни `git fetch origin` и обнови чистый `main` fast-forward до
   `origin/main`. Чужие изменения сначала сохрани и согласуй владение затронутыми
   файлами. Не создавай feature-ветку без явного запроса пользователя.
2. Проверь актуальные назначения в TASKS. Раздели задачу на независимые части
   Frontend, Backend и Logic в пределах единственной таблицы AGENT_PLAN.
   Передай каждому конкретному исполнителю задачу, свежий полный SHA, рабочую
   папку, точные файлы, зависимости и критерии приёмки по START_HERE.
   Не назначай одного файла нескольким активным исполнителям.
3. В общем дереве выполняй Git-операции централизованно. Fetch/fast-forward
   проведи до запуска подзадач; не меняй общую базу под работающими исполнителями.
   Координируй зависимости и общие проверки. Публичные изменения контракта
   согласуй с потребителями один раз; несовместимые обходы не допускаются.
4. Принимай результаты по handoff: проверь область diff, выполненные проверки
   и ограничения. Интеграционная роль не даёт права параллельно редактировать
   активные файлы другого исполнителя; сначала согласуй передачу владения.
   Обновляй TASKS и STATUS по фактам, сохраняя исторические записи.
5. Подключи Reviewer к конкретному согласованному SHA либо зафиксированному
   набору изменений документации. Для документации достаточно ссылок,
   согласованности инструкций и diff. Для продуктовых изменений проведи
   необходимые тесты и приёмку M1–M5/пользовательского пути по масштабу изменения.
   Дефекты возвращай владельцам и повторяй затронутые проверки после исправлений.
6. После каждого завершённого и проверенного блока просмотри diff и staged-файлы,
   создай коммит относящихся к нему файлов и сделай push в `origin/main`.
   Это постоянное поручение пользователя; повторное разрешение не требуется.
   Перед push проверь удалённый main. Если он изменился, завершив/приостановив
   параллельную работу, интегрируй изменения без переписывания истории и повтори
   необходимые проверки. Не используй force push, reset --hard или `git add -f`.
   Новое явное указание «без commit/push» имеет приоритет.
7. Сообщи итоговый SHA, фактические проверки, ограничения и подтверждённый
   статус push. Секреты, сырые данные и чужие несвязанные правки не включай.
   Деплой, официальная сдача и отправка заказов требуют отдельного поручения.

Не блокируй независимую работу ожиданием оригиналов. Не называй импорт
проверенным на них без фактической проверки и не выдавай локальную готовность
за официальную сдачу. Единоличный исполнитель прямого поручения пользователя
выполняет также функции интегратора и тот же цикл обновления/публикации.
