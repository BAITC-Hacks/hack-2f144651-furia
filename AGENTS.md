# EKT — инструкции для всех агентов

Официальный репозиторий Furia: `https://github.com/BAITC-Hacks/hack-2f144651-furia.git`.
Приложение уже существует. Продолжайте MVP, сохраняйте Python/Streamlit и отвечайте
по-русски. Сначала прочитайте [START_HERE](START_HERE.md),
[актуальные задачи](docs/TASKS.md), [состояние](docs/STATUS.md),
[план ролей](docs/AGENT_PLAN.md), [архитектуру](docs/DEVELOPMENT.md)
и один промпт своего назначения.

## Роли и общий контракт

- Направления разработки: **Frontend, Backend, Logic**. **Интегратор** координирует
  общие изменения и публикацию; **Reviewer** выполняет независимую проверку.
- [AGENT_PLAN](docs/AGENT_PLAN.md) — единственная нормативная таблица владельцев
  и разрешённых файлов. Вложенные AGENTS уточняют технические инварианты.
  Архитектурное описание и исторические отчёты не создают других назначений.
- Задачу, исполнителя/сессию, полный базовый SHA, файлы, зависимости и критерии
  приёмки фиксируйте по [TASK_TEMPLATE](docs/TASK_TEMPLATE.md) в TASKS либо
  связанном документе задачи. Не занимайте активную задачу другого исполнителя.
  Одно поручение пользователя может включать координацию и ограниченные подзадачи;
  наличие ролевого промпта само по себе не запускает все направления.
- Один файл одновременно меняет один исполнитель. При чужих изменениях в нужных
  файлах согласуйте передачу; независимую работу продолжайте. В общем дереве
  исполнители меняют назначенные файлы, Git выполняет интегратор.
- Реальный API — код и [INTERFACES](docs/INTERFACES.md). Не создавайте второй Bundle,
  `contracts.py`, `normalize.py` или `replenish.py`. Общий контракт, fixtures,
  зависимости и общие документы согласуются с интегратором. Он может делегировать
  конкретную подзадачу своей зоны с явным назначением файлов.
- Frontend вызывает ekt в том же Python-процессе; отдельного HTTP API нет.
  Backend/Logic не импортируют Streamlit или ekt_ui. Формулы не копируются в UI.
  Каждый исполнитель ведёт свой handoff; Reviewer не правит продуктовый код.

## Git

Постоянное указание пользователя от 23.09.2026: **перед каждой новой задачей
проверять свежий main; после каждого завершённого и проверенного изменения,
включая документацию, делать commit и push в `origin/main`**. Повторное разрешение
не требуется. Новое явное указание пользователя, например «без commit/push»,
имеет приоритет. Деплой, официальная сдача и отправка заказов требуют отдельного
поручения.

1. Перед работой выполните `git status --short --branch`, `git rev-parse HEAD`,
   `git fetch origin`. По умолчанию работайте в `main`; новую ветку/worktree
   создавайте только по явному поручению. При отсутствии отслеживаемых правок
   обновите `main` через `git merge --ff-only origin/main`. Сохраните локальные
   файлы; если они мешают обновлению, разрешите ситуацию без перезаписи.
   При расхождении истории сначала выясните источник локальных коммитов.
2. В общем working tree интегратор выполняет обновление один раз до запуска
   параллельного этапа и передаёт полный SHA исполнителям. Исполнители сверяют
   HEAD и свои файлы, но не запускают собственные fetch/merge/checkout/add/commit/push
   и не меняют Git под работающими соседями. Это единый цикл обновления main
   для назначенных подзадач, а не исключение из требования свежей базы.
3. После проверок просмотрите diff. Добавляйте только файлы завершённой задачи
   явным списком; чужие правки, сырые данные и секреты не включайте. В общем
   дереве проверенные результаты подзадач коммитит интегратор.
4. Перед публикацией снова выполните `git fetch origin`. Если main продвинулся,
   согласуйте завершение активных записей в общем дереве, сохраните свою работу
   коммитом и объедините новый `origin/main` без переписывания истории. Конфликты
   решайте с учётом обеих сторон; повторите затронутые проверки. Не делайте pull
   или автоматический stash поверх незавершённых чужих правок.
5. Выполните `git push origin main`, затем проверьте удалённый SHA. Если push
   отклонён из-за нового main, повторите fetch/интеграцию/проверки. При ошибке
   проверки или недоступной публикации сообщите фактический блокер; не называйте
   изменения опубликованными до подтверждения.

Сохраняйте действующие remotes, Git-историю и чужие файлы. Запрещены `git init`,
смена origin, force push, `reset --hard`, `git add -f`, копирование чужого `.git`
и перезапись дерева. Проверка только чтением без изменений не требует пустого коммита.

## Инварианты и готовность

- Числа рассчитываются локально; API-ключ для основного сценария не нужен.
  Нет отправки заказов или исходных данных внешним сервисам.
- Синтетика, данные партнёра и ручные допущения различаются. Неизвестное
  не подменяется нулём или выдуманным фактом.
- Сохраняйте строковые коды, единицы, scope, происхождение и знаки продаж.
  Не суммируйте историю с детализацией, снимки остатков по времени и резерв повторно.
- Документ не является клиентом; месячный нулевой остаток не доказывает дни
  stockout. IEK month_start не является текущим остатком.
- Все M1–M5 обязательны для полной продуктовой приёмки. Макеты не заменяют
  проверку оригиналов. Набор проверок выбирайте по объёму задачи из AGENT_PLAN.
- Сырые архивы, клиентские записи, секреты и диагностические выгрузки не коммитьте.
- Учитывайте фактическое время: в комплекте дедлайн 23.09.2026 18:00 Asia/Almaty;
  уточнения организаторов имеют приоритет. Поздние изменения не выдавайте за своевременные.
- Сообщайте выполненные проверки, реальные ограничения и статус публикации.
  Локальная готовность, push и официальная сдача — разные результаты.
